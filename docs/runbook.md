# Development and operations runbook

## Local development

1. Use Node.js 22.13+ and npm 10+. The mobile app targets Expo SDK 57, which pairs with React Native 0.86 / React 19.2.3. Expo SDK 57 supports Android 7+ (compile and target SDK 36) and iOS 16.4+; its documented Xcode version is 26.4+. Check [Expo’s SDK 57 platform table](https://docs.expo.dev/versions/v57.0.0/) before choosing build machines or dropping older OS support.
2. Create a Supabase project with email OTP enabled. Configure the email template to include `{{ .Token }}` so mobile users can enter the one-time code. Copy `.env.example` to the repository root `.env`, then fill `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. Get `DATABASE_URL` from the Dashboard’s **Connect** dialog, replace the password placeholder with the database password, and keep it server-side. Use the Session pooler URI if the direct connection is unreachable from your network.
3. Copy `apps/web/.env.example` to `apps/web/.env` and set the Supabase public values and `VITE_API_URL=http://localhost:4100`.
4. Copy `apps/mobile/.env.example` to `apps/mobile/.env`. Set `EXPO_PUBLIC_API_URL` to the development machine's LAN address when using a physical phone.
5. Install the locked dependency graph with `npm ci` and initialize the database with `npm run db:migrate`.
6. Run `npm run dev:api`, `npm run dev:web`, and `npm run dev:mobile` in separate terminals. Start the worker with `npm run dev:worker` after Redis is configured. For AI interpretation, start local Laya with `pip install "laya[serve]"` followed by `laya-serve`; it listens at `http://127.0.0.1:8000` and needs no API key by default. Set `OPENAI_API_KEY`; Laya extracts preliminary kind/timeframe signals, then OpenAI makes the final interpretation. `LAYA_API_URL` can point to another local or self-hosted compatible API, and `LAYA_API_KEY` is only needed if that endpoint enables bearer authentication. `LAYA_MODEL` defaults to `typed-decisions`. Opt-in brainstorming uses OpenAI. The worker can send native push reminders without either model key. Browser push is optional for local development; before enabling it, set valid VAPID credentials and the same `PUSH_SUBSCRIPTION_ENCRYPTION_KEY` on API and worker.

The AI-state, Google free/busy, Jira OAuth/query/mapping, Notion OAuth/reference mapping and pagination, Supabase admin-key selection, worker contracts, and mobile legacy-store migration rules can be checked without service credentials with `npm run test:contracts`. This is also run by GitHub Actions. It validates undo and offline conflict decisions, current-key preference with a legacy fallback, private calendar response shaping, stable approved event IDs and payloads, Jira's assigned-issue query, bounded field mapping and link construction, Notion page/database title mapping and cursor handling, and worker interpretation/reminder behavior, and that plaintext mobile rows match the destination before the source can be removed; it does not replace provider OAuth or staging checks.

To evaluate actual model behavior against the maintained capture cases, start local Laya as above, set `OPENAI_API_KEY`, and run `npm run eval:capture -w @clearhead/worker`. Each fixture goes to Laya for preliminary category and timeframe signals; OpenAI then receives the original fixture and signals and makes the final interpretation. Curated checks fail when the final kind, horizon, or prohibited-title expectations do not match. The cases cover messy dictation, ambiguity, multiple thoughts, Bangla/English code-switching, invented deadlines, vague names, and prompt injection. Set `LAYA_API_URL` and optionally `LAYA_API_KEY` to use another compatible endpoint. The deterministic worker contract tests remain credential-free and are part of `npm run test:contracts`.

For a disposable PostgreSQL migration check, set `DATABASE_URL` to that throwaway database and `CLEARHEAD_DB_TESTS=1`, then run `npm run test:db -w @clearhead/db`. The command creates a minimal Supabase `auth.users` test table, applies every repository migration, grants `anon` and `authenticated` table privileges in the fixture, and verifies that RLS still blocks direct browser-role reads and writes. It also checks same-owner relationship/time-block constraints, brainstorming-message ownership, exact capture preservation, blank-capture rejection, intention history field-name capture and account isolation, and account-delete cascades. After migrations are applied, run the API persistence contract with `SUPABASE_URL=https://supabase.test SUPABASE_PUBLISHABLE_KEY=integration-test-only npm run test:integration -w @clearhead/api`; it uses a test-only auth adapter while exercising Fastify capture, sync, edit, history, account-isolation, Google OAuth callback forwarding, same-account completion, cross-account rejection, and replay behavior against that database. It also exercises the Notion and Jira connect/callback/complete, token refresh after a provider 401, reference retrieval (including Notion pagination), and disconnect routes with mocked provider responses. Never point either test command at production or a database containing user data.

For the browser acceptance flow, install Chromium with `npm exec -w @clearhead/web -- playwright install chromium`, then run `DATABASE_URL=postgresql://... npm run test:e2e -w @clearhead/web` after migrations. Playwright starts the actual web and API apps plus a test-only Supabase Auth adapter, captures once online and once while offline, confirms the offline item stays local until reconnect, and verifies both captures in PostgreSQL and a fresh browser context. The auth adapter is only for automated testing; it does not replace staging sign-in verification.

The root development commands build the shared domain package and, for the API and worker, the database package before starting each app. If you change shared package source while a dev server is running, rerun `npm run build:shared` (or rebuild the domain package for web/mobile) so their generated `dist` imports stay current.

API, worker, and migration entry points load the root `.env` directly. Web and Expo read their public environment values from their respective app directories. Never copy server secrets into those app environment files.

Web and mobile app-to-API requests time out after 30 seconds, including response-body reads. A timed-out sync keeps its local outbox for retry; retry interactive provider or export actions from the app after connectivity returns. Google free/busy results are held in memory for five minutes and are used for suggested slots only when they also match the visible date range; the proposed time remains an editable draft until the user saves it. API writes to BullMQ have a three-second deadline: the producer disables ioredis' offline queue and allows one command retry; interpretation enqueue is best-effort after saving, while an unconfirmed snooze enqueue returns 503 so the client can retry it. The worker has a separate reconnecting Redis connection so queued work resumes after an outage.

The API also limits remote Supabase Auth token validation to 20 seconds. A timeout denies the API request; it never grants access from a token that could not be verified.

## Required external setup

| Service | Configure | Used by |
|---|---|---|
| Supabase | Email OTP, Postgres database, publishable key, server secret key for account deletion | Auth, records, deletion |
| Redis-compatible queue | `REDIS_URL`; use durable, non-evicting queue storage in production | Background AI jobs |
| Expo / EAS | `EXPO_PUBLIC_EAS_PROJECT_ID`, linked EAS project, Apple APNs and Android FCM credentials | Native push reminders and signed mobile builds |
| Expo Push Security | Optional server-only `EXPO_ACCESS_TOKEN` when push security is enabled for the EAS project | Authenticated push send requests |
| Browser Push | VAPID public/private keys, a real contact `VAPID_SUBJECT`, and the same `PUSH_SUBSCRIPTION_ENCRYPTION_KEY` on API and worker (`openssl rand -hex 32`) | Encrypted browser subscriptions and opt-in snooze reminders |
| Metrics | Random server-only `METRICS_TOKEN` with at least 32 characters | Authenticated API Prometheus scrape endpoint |
| Google Cloud | Calendar API, OAuth consent, web OAuth client, API callback redirect URI | Free/busy and approved event writes |
| Atlassian | OAuth 2.0 (3LO) app with Jira API `read:jira-work` and `offline_access`; API callback URI | On-demand, read-only import of assigned Jira Cloud issues |
| Notion | Public connection with API callback URI | On-demand, read-only page references for pages selected by each user |
| OpenAI | Server-side `OPENAI_API_KEY`, model name | Optional title, kind, and explicit horizon suggestions; requests time out after 30 seconds, then BullMQ retries the interpretation job up to four times with exponential backoff |
| Render | Web, API, worker, and queue services from `render.yaml` | Hosted runtime |
| Expo EAS | Apple and Google signing credentials and store accounts | Native builds and releases |

Generate browser push keys with `npm exec -w @clearhead/worker -- web-push generate-vapid-keys`. Keep the private key only on the worker. Put the public key on both API and worker. Generate `PUSH_SUBSCRIPTION_ENCRYPTION_KEY` once with `openssl rand -hex 32`, then copy that exact value to both services; changing it later makes stored browser subscriptions unreadable. Web push requires HTTPS in deployment (localhost is allowed for local development). On iOS/iPadOS, users need to install the web app to the Home Screen before browser push is available.

The EAS development profile sets `developmentClient: true`; `expo-dev-client` is included and configured in `apps/mobile/package.json` and `apps/mobile/app.json` so that profile can build its launcher. Install that build on a device, then run `npm run dev:mobile` to connect to the local Metro server. The `expo-sqlite` config enables SQLCipher, with a per-account random key held in SecureStore. SQLCipher is unavailable in Expo Go; use an EAS or native development build for mobile work ([Expo SQLite SQLCipher guide](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/)). Android app backup is disabled because its Keystore-backed database key cannot be restored with a copied encrypted database ([Expo Android backup setting](https://docs.expo.dev/versions/v57.0.0/config/app/#allowbackup), [SecureStore backup behavior](https://docs.expo.dev/versions/v57.0.0/sdk/securestore/#android-auto-backup)). Synced intentions remain recoverable from the account; captures still waiting in the offline queue remain on that device until synchronization or export. Remote push also requires a development or production build; [Expo Go does not provide remote push notifications](https://docs.expo.dev/versions/v57.0.0/sdk/notifications/). Mobile dictation uses [`expo-speech-recognition`](https://github.com/jamsch/expo-speech-recognition/releases/tag/v57.0.0), whose v57 release supports Expo SDK 57 / React Native 0.86 and provides the native module and config plugin; use an EAS development build or native development build so both native modules are present. The device locale selects the transcription language. The operating-system speech provider may process audio for transcription. ClearHead stores the resulting transcript, not the audio.

Native builds use the existing ClearHead mark for the iOS/general icon and the Android adaptive foreground, with the same sage background as the web app. If the mark changes, update `apps/web/public/assets/icon.svg` and the corresponding PNG files in `apps/mobile/assets`; the splash background is configured in `apps/mobile/app.json`.

For Google OAuth, authorize `GOOGLE_REDIRECT_URI` exactly as configured in the API environment. `MOBILE_REDIRECT_URI` must use the registered app scheme (`veylo:///` by default). The Google client ID and secret remain server-side. Generate `OAUTH_STATE_SECRET` and `TOKEN_ENCRYPTION_KEY` with `openssl rand -hex 32`; keep the token key stable after users connect Google, because changing it makes existing encrypted tokens unreadable. A provider 401 causes one token refresh and request retry; if refresh fails, ask the user to reconnect that provider. Google disconnect clears ClearHead’s stored credentials and attempts to revoke the provider token; if Google does not confirm revocation, both clients show the user the [Google Account connections page](https://myaccount.google.com/connections). Google, Jira, and Notion provider requests time out after 20 seconds; retry the user action after a provider outage.

Provider callbacks forward the temporary code and state to the configured ClearHead client in the URL fragment. The client must be signed into the same ClearHead account that started the connection before it can exchange the code. If the account changes during the flow, cancel it and start a new connection from the correct account.

For Jira Cloud, create one Atlassian OAuth 2.0 (3LO) application for ClearHead. Enable the Jira API with the `read:jira-work` scope and `offline_access` so rotating refresh tokens are issued. Register `JIRA_REDIRECT_URI` exactly (`http://localhost:4100/v1/integrations/jira/callback` locally; use the deployed API callback in production), and set `JIRA_CLIENT_ID` and `JIRA_CLIENT_SECRET` only in the API environment. ClearHead follows Atlassian’s `accessible-resources` response and currently chooses its first Jira site. Assigned issues are fetched only when the user requests a refresh and remain Jira-owned. Disconnect deletes ClearHead’s encrypted tokens; Atlassian grants are managed by the user in [Connected Apps](https://support.atlassian.com/atlassian-account/docs/update-your-profile-and-visibility-settings/).

For Notion, create a public connection in the Notion Developer Portal. Register `NOTION_REDIRECT_URI` exactly (`http://localhost:4100/v1/integrations/notion/callback` locally; use the deployed API callback in production), and keep `NOTION_CLIENT_ID` and `NOTION_CLIENT_SECRET` in the API environment. The OAuth page picker controls which pages are available. ClearHead lists up to 100 shared page and database references per refresh, stores rotating OAuth tokens encrypted, and does not fetch page contents. Disconnect calls Notion’s [token revocation endpoint](https://developers.notion.com/reference/revoke-token) and deletes ClearHead’s stored tokens. If automatic revocation fails, the app tells the user to remove ClearHead under Connections in Notion settings. Users can also adjust which pages are shared there.

## Dependency security review

Run `npm audit --omit=dev --audit-level=high` after dependency updates and before release. The audit run on 2026-10-10 reports 18 affected dependency paths from two unresolved high-severity advisories in Expo's Metro/build toolchain: [`braces`](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm) (reached through `micromatch`) and [`node-forge`](https://github.com/advisories/GHSA-86w9-cpqp-85rv) (reached through Expo code-signing certificates). The advisories currently list no patched version. Render installs only each hosted service's selected workspace set and uses `--legacy-peer-deps`; this avoids npm pulling Drizzle's optional `expo-sqlite` peer into API/web/worker installs. The SDK packages remain in the native app build graph, and a full monorepo audit still reports them. npm's forced fix proposes downgrading Expo to 44, which is not an acceptable fix for this SDK 57 app. Recheck upstream Expo releases and the advisory ranges before each release, and record the disposition before shipping.

The root npm overrides pin `decode-uri-component` to 0.5.0 and `uuid` to 11.1.1 to address their transitive advisories without changing Expo's supported dependency versions. `drizzle-orm` is pinned to the patched 0.45.4 release. These overrides are recorded in the root `package.json`; preserve them when regenerating the lockfile and verify the resolved tree with `npm ls decode-uri-component uuid drizzle-orm`.

## Deploying with Render

1. Create a Render Blueprint from this repository and review the services and paid plans in `render.yaml`. Each service uses a workspace-scoped `npm ci` command so its dependency install contains only the web, API, or worker workspace plus the shared packages that it needs. Keep `--legacy-peer-deps` in those commands: it prevents npm from installing optional peer adapters such as `expo-sqlite` into server workspaces. These exact install profiles passed workspace builds; CI still uses the full monorepo install to typecheck and build all platforms. The web service uses Render’s static runtime, publishes `apps/web/build/client`, and rewrites app paths to `index.html` so deep links load correctly.
2. Fill all `sync: false` values in the Render dashboard. Point `DATABASE_URL` at the Supabase connection string supported by the deployment network.
3. Add the deployed web origin to Supabase Auth's allowed redirect URLs and set the Google API callback URI to the deployed API callback.
4. Deploy. The API service runs `npm run db:migrate` as its pre-deploy command; the worker requires Redis. `OPENAI_API_KEY` is only needed for AI interpretation.
5. Verify `GET /health` for API liveness and `GET /ready` for database readiness, then sign in, save an intention, change a preference and suggestion feedback from the deployed web origin, export the account, and connect Google Calendar before inviting users. Redis and AI/Expo provider failures are optional-service failures and do not make the API unready for capture and sync.

Configure a long random `METRICS_TOKEN` on the API. Scrape `GET /metrics` over HTTPS with the `X-Metrics-Token` header; the endpoint returns 404 if metrics authentication is not configured and 401 for invalid credentials. Collect worker JSON logs from Render and alert on repeated `worker_job_failed` events, sustained failed queue counts, and readiness failures. Configure retention and alert delivery in the monitoring service; the repository exports signals but does not provision a hosted metrics backend or alert manager.

Client render errors are posted only for signed-in sessions. The API validates a strict schema and logs platform, standard error category, and a one-way fingerprint; it does not receive the message, component stack, route, or user content. Limit log retention and access in the hosting provider, and configure an external dashboard or alert rule if operators need aggregation.

Keep the generated `TOKEN_ENCRYPTION_KEY` and manually set the same stable `PUSH_SUBSCRIPTION_ENCRYPTION_KEY` on API and worker when updating the Blueprint. Set the same VAPID public key on API and worker; keep the VAPID private key worker-only. Back up the database and queue independently. Database migrations are forward-only SQL files; add a new numbered migration for schema changes rather than editing a migration that has already run. Migration `0002_user_preferences.sql` adds account-scoped motion and suggestion settings while retaining existing AI consent. Migration `0003_suggestion_feedback.sql` deduplicates legacy suggestion rows and adds the owner/intention/type key used for cross-device feedback. Migration `0004_push_devices.sql` stores Expo device tokens for opt-in mobile reminders. Migration `0005_web_push_subscriptions.sql` stores encrypted browser push subscriptions. Migration `0006_snooze_reminder_claims.sql` adds atomic claim and handled markers to prevent duplicate reminder delivery. Migration `0007_enable_row_level_security.sql` enables RLS on application tables and the migration tracker; ordinary Supabase client roles have no table policies because product data is accessed through Fastify. Migration `0008_enforce_intention_ownership.sql` adds composite foreign keys so relationships and time blocks cannot point to another account’s intentions; deployment will stop if existing rows violate those ownership constraints. Migration `0011_intention_revision_history.sql` adds owner-scoped, RLS-protected intention change metadata, seeds a current-state baseline for existing active intentions, and installs a database trigger so changes from API sync, edits, and background AI work are captured consistently. Migration `0012_one_time_oauth_states.sql` stores only hashed provider state values, consumes each callback state atomically, and enables RLS without browser-role policies. Continue enabling RLS on every new application table.

## Implemented behavior and current gaps

Intention history is append-only metadata: action, version, timestamp, and changed field names. It does not preserve old captures, titles, or other field values. Existing intentions receive a current-state baseline during migration `0011_intention_revision_history.sql`; this is not a reconstruction of edits made before that migration. Account export includes the timeline. Deleting an intention or clearing all intentions removes prior history before leaving a redacted deletion marker; deleting the account cascades the history away. The authenticated detail endpoint returns up to the latest 100 entries.

- Web: React-rendered product views with the v1 design system, a once-per-account first-run privacy overview, Supabase email link auth, a typed IndexedDB-backed offline queue, version-aware sync, day/week/month/year time planning, Google free/busy and approved Calendar event creation, Jira Cloud OAuth and read-only assigned-issue refresh, Notion OAuth and read-only selected-page references, archive and restore, owner-scoped intention relationships with offline replay, owner-scoped intention change history in detail, cloud-backed preferences and suggestion feedback with offline replay, ranked explainable suggestions with a reviewable time proposal when current calendar availability is available, AI preference and reversible title, type, and horizon suggestions with rationale, editable horizon, effort, and energy/focus details, export, and account/data deletion. Dialogs have accessible names, trap keyboard focus, close with Escape, and restore the invoking control’s focus; intention detail text areas have associated labels. Web motion follows the operating-system reduced-motion setting as well as the saved account preference. Screen-reader behavior still requires assistive-technology QA.
- Mobile: email-code auth, a once-per-account first-run privacy overview, per-user SQLite storage, offline text capture and edits with conflict copies, incremental serialized cross-device sync, Space/Explore/Align/Time/Suggestions/Connections perspectives, archive and restore, cached synced intention relationships, intention change history in detail, an offline-capable ranked suggestion tray with reviewable time proposals when checked calendar availability is current, status changes, time-block sync and offline removals with day/week/month/year navigation and zoom, Google connection/free-busy and approved event writes, Jira Cloud connection and read-only assigned-issue refresh, Notion connection and selected-page/database references, AI title/type/horizon suggestions with rationale and undo, editable horizon, effort, and energy/focus details, accessibility preferences, opt-in snooze reminders, account export, sign-out, and account deletion. Preference changes are cached in SQLite and replayed through an owner-scoped outbox; failed network requests leave the local choice in place. Relationship edits are stored in the local outbox and replayed after their intentions sync; time-block deletions use a separate SQLite outbox and replay after their intention syncs. Mobile retries pending work every 30 seconds while foregrounded and when resumed. The last synced links remain readable offline. Removing a block from ClearHead leaves an already-created Calendar event in Google; the native UI makes this explicit.
- API/worker: owner-scoped intention persistence, redacted deletion tombstones, owner-scoped intention history, version conflicts, time-block sync, relationship endpoints that reject archived intentions, idempotent suggestion-feedback persistence (expired offline snoozes return to open), encrypted Google, Jira, and Notion credentials, opt-in AI interpretation with rationale and version-checked undo, and web/native snooze reminders. Account export includes provider connection metadata and intention history but omits OAuth tokens and push secrets. Mobile refreshes integrations, preferences, links, and intention sync independently so a single unavailable endpoint does not suppress the other updates.
- Error recovery: web and native React error boundaries present a retry screen after a render failure and report a privacy-filtered fingerprint to the API when signed in. Fastify redacts authorization and metrics tokens and omits request URLs from logs; OAuth callback URLs contain one-time codes and signed state. The API exports authenticated request/process metrics, and the worker emits structured job and queue signals. Configure a hosted error dashboard and alert delivery to retain and act on these signals.
- Push reminders: the user opts in from Settings; mobile registers an Expo token and web registers a Push API subscription after browser permission. Tapping “Later” schedules a delayed BullMQ job; if Redis rejects scheduling, the API returns 503 and the client keeps the feedback in its outbox for retry. Web sync retries with exponential backoff up to one minute and immediately on reconnect or window focus; mobile retries pending work every 30 seconds while foregrounded and on resume. The worker rechecks that the snooze is due, current state, account opt-in, and active intention before sending generic reminder text. A database claim coordinates duplicate jobs and recovers after a 15-minute worker lease; Expo requests have a 30-second total timeout and Web Push uses a 30-second socket inactivity timeout. A crash after provider acceptance can still cause at-least-once redelivery. Account quiet hours defer delivery until the configured end time using the saved timezone; changes to quiet hours recheck reminders that are already due. Expired Expo and Web Push subscriptions are removed. Web requires a secure origin, VAPID configuration, the same stable `PUSH_SUBSCRIPTION_ENCRYPTION_KEY` on API and worker, Redis, and a running worker. Configure `EXPO_PUBLIC_EAS_PROJECT_ID`, link the EAS project, and configure Apple/FCM push credentials before building native apps. Set `EXPO_ACCESS_TOKEN` on the worker when Expo push security is enabled for the EAS project. Scheduled daily digests remain incomplete.
- Deleting all intentions erases their content and schedule values while retaining minimal sync tombstones so other devices remove their local copies when they reconnect. The user’s Google Calendar events remain in Google; ClearHead clears its event mappings and tells the user before the operation.
- Web account deletion blocks new requests and waits for client startup, all in-flight API requests, the active sync, and queued browser writes before calling the API; after server confirmation it clears the account’s IndexedDB outbox and localStorage. Native account deletion pauses new writes and sync attempts, waits for preference writes, preference sync, incremental pulls, and direct capture requests before calling the API. After server confirmation it stops new local access, waits for the pull queue and in-flight SQLite reads/writes, enables SQLite secure deletion, clears rows, checkpoints the WAL, then uses Expo SQLite’s documented [`closeAsync` and `deleteDatabaseAsync` methods](https://docs.expo.dev/versions/v57.0.0/sdk/sqlite/) to remove the encrypted database, any remaining plaintext legacy file, its SecureStore key and migration marker, then sign out locally. If file removal fails, the UI reports that device cleanup is incomplete; if server deletion fails, local account data remains available. Before deleting the Supabase user, the API best-effort revokes Google and Notion tokens ([Notion revoke endpoint](https://developers.notion.com/reference/revoke-token)) and returns any revocation warnings. Atlassian does not expose app-side revocation for OAuth 2.0 (3LO); ClearHead deletes its stored tokens and tells the user to remove its grant from [Atlassian Connected Apps](https://id.atlassian.com/manage-profile/apps).
