# Production application stack

**Status:** accepted

Veylo will use a TypeScript monorepo with **React Router Framework Mode** for the web client, **Expo Router / React Native** for iOS and Android, and a standalone **Fastify** API. Web and mobile will share domain schemas, API contracts, and design tokens, while keeping platform-specific UI and offline storage. The API owns intention writes, sync, AI requests, and provider integrations so secrets and external writes stay server-side.

The API will use **Supabase Auth** for identity and **Supabase Postgres** for durable data, accessed through **Drizzle ORM** and versioned migrations. The API validates user sessions and scopes every query to the authenticated owner. Clients keep an offline-first local store (IndexedDB on web; SQLite on mobile) and synchronize through idempotent API operations. Background AI interpretation and delayed reminders run in a separate worker using **BullMQ** with a managed Redis-compatible queue. Provider reads currently run on demand through API adapters; external changes always require user approval.

Deploy the web app, API, and worker on **Render**; use **Expo Application Services** for native builds and release delivery. Start with an installable web app on Windows; evaluate a packaged Windows client only if user needs justify maintaining it. Keep AI and provider implementations behind adapters, with Google Calendar writes gated by user approval and Jira/Notion limited to read-only V1 imports.

This separates the immersive web experience from native mobile interaction while retaining shared product rules. React Router Framework Mode is selected over Next.js because Veylo is an authenticated, interactive workspace and benefits more from React continuity with Expo than from Next-specific server component features. A standalone API remains the shared boundary for mobile, web, jobs, and integrations. Supabase supplies managed Postgres and authentication; Drizzle keeps schema and migrations in the repository. Render provides web, API, and worker service types, while EAS handles native distribution.

**Consequences:** this is more code than a single web app, but it supports real mobile behavior, durable multi-device data, offline capture, and secure provider sync. Shared packages will contain domain rules and contracts, not an attempt to force identical UI across browser and native platforms. Provider tokens must be encrypted at rest, and OAuth flows must complete through the backend. Exact account configuration, deployment regions, and production secrets are environment setup, not committed values.
