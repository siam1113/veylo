## Release gates

Capture now accepts up to 8,000 characters across shared validation, API sync, web/mobile input, and Postgres. Migration `0013_expand_raw_capture_limit.sql` updates existing databases. The current host passes 24 domain tests, including long-capture and dictation-merge coverage. The PostgreSQL migration contract checks that exactly 8,000 characters are accepted and 8,001 are rejected. A manual SQL-only rehearsal applied all 13 migrations to a disposable PostgreSQL 16 container and passed direct checks for RLS, same-owner constraints, revision history, the 8,000-character boundary, and account-deletion cascades. The package-backed migration contract and API persistence checks still need to run after a complete dependency install.

The repository has a committed npm lockfile and CI/Render use `npm ci`. A clean Node.js 22 Linux container previously completed `npm ci`, all workspace typechecks, production builds for web/API/worker and iOS/Android bundles, the PostgreSQL migration contract, two API integration tests (capture/edit/history/account isolation and OAuth callback/account binding/replay), and the Playwright online/offline capture and reconnect flow against PostgreSQL. After that clean run, API/worker/mobile contract tests and PostgreSQL-backed Google, Notion, and Jira OAuth lifecycle tests were added; the new database-backed tests have not yet run. On this macOS host with Node.js 22.20, `npm run test:contracts` passed all 31 focused API, worker, and mobile checks and the shared domain package compiled with the cached TypeScript compiler. A fresh `npm ci` cannot complete because registry requests fail with `ENOTFOUND`; an isolated offline install also stops because the locked `openai@5.23.2` tarball is absent from npm's cache. The current workspace is therefore incomplete. Current builds cannot be repeated here: the web build stops because the React Router CLI is missing, and the shared workspace build stops in the DB package because `postgres`, Drizzle, dotenv, and Node type definitions are absent. Full workspace typecheck/build must be rerun after the locked install succeeds. The Playwright offline-capture regression was attempted but cannot start because Playwright is missing; it was added after the earlier clean run. The command is wired into GitHub Actions, but the updated workflow has not yet run remotely. The scoped Render web/API/worker installs also passed their builds; those installs omit Expo's optional toolchain peer, which remains in the native build dependency graph. Browser and API integration tests use a test-only Auth adapter; they do not replace real Supabase sign-in or provider consent checks. The 2026-10-10 audit reports 18 high-severity dependency paths from two unresolved Expo toolchain advisories (`braces` and `node-forge`); neither currently has a patched version. npm's forced fix downgrades Expo to SDK 44, which is incompatible with this app. See the [dependency security review](runbook.md#dependency-security-review) before release.

The v1 definition of done also requires empirical capture-latency measurement, loss-of-connectivity/app-restart checks, real-device iOS and Android QA, browser and native accessibility review, provider OAuth and retry checks, and store policy review, including the SQLCipher encryption declaration. In the current workspace, root/web/mobile `.env` files are absent, Android `adb` is unavailable, and `xcrun simctl` cannot connect to CoreSimulator. Live Supabase/provider checks and native device QA were therefore not run. Complete these gates with configured Supabase, Redis, Google OAuth, push credentials, signing accounts, and supported devices; code inspection does not substitute for those checks.

Jira and Notion read-only reference adapters are present as additional integrations. Query/reference mapping and pagination contracts run through `npm run test:contracts`; PostgreSQL-backed lifecycle tests now cover OAuth state, token exchange, refresh after a provider 401, data retrieval, and disconnect using mocked provider responses. Those lifecycle tests still need a complete dependency install and PostgreSQL run. Real provider consent, credentials, and staging validation also remain release checks; these adapters are not part of the V1 must-ship list in the plan.
