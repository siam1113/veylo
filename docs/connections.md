# Connections setup

The Connections tab supports 13 services: Google Calendar, Outlook Calendar, iCloud Calendar, ClickUp, Asana, Trello, Jira Cloud, Notion, Todoist, Microsoft To Do, Linear, GitHub Issues, and Slack. Connections read data on demand; only Google Calendar creates approved events. Previews disclose their limits and whether more items exist.

Outlook previews the next 30 days in the default calendar. iCloud previews the next 30 days across up to five calendars, capped at 100 events. ClickUp, Asana, Trello, Linear, and GitHub show open assigned tasks/cards/issues. Todoist includes open tasks in shared projects; Microsoft To Do reads up to five lists. Work previews show up to 100 items. Slack previews the 50 most recent searchable messages sent by the connected user. **Keep as thought** explicitly saves the selected message text and source link through Veylo's existing durable local queue; it does not post to Slack. Provider preview contents otherwise remain in memory rather than being imported into thoughts automatically.

If Connect previously displayed a generic warning, check the API environment: missing provider credentials were producing HTTP 503, which the server intentionally masked as an internal error. The catalog now exposes only configuration readiness, the UI labels missing setup, and Connect returns an actionable 409 if called before configuration. Access-token-only connections (including ClickUp) are recognized without requiring a refresh token. OAuth returns to Connections and reports its result inline.

1. Apply migrations using `npm run db:migrate`; `0014_more_connection_providers.sql` and `0016_personal_and_team_connections.sql` extend the one-time OAuth state provider constraint. Render runs migrations before deployment.
2. Set `OAUTH_STATE_SECRET` (at least 32 random characters) and `TOKEN_ENCRYPTION_KEY` on the API. Keep existing values when upgrading; replacing the encryption key makes existing tokens unreadable. Never put secrets in `VITE_` variables.
3. Register each desired OAuth provider app. Set its `*_CLIENT_ID`, `*_CLIENT_SECRET`, and `*_REDIRECT_URI` on the API (see `.env.example` and `render.yaml`). The redirect must exactly match `https://YOUR_API/v1/integrations/PROVIDER/callback`, where PROVIDER is `google`, `outlook`, `clickup`, `asana`, `trello`, `jira`, `notion`, `todoist`, `microsoft_todo`, `linear`, `github`, or `slack`. Environment prefixes use the uppercase provider ID, including `MICROSOFT_TODO`. Asana requires HTTPS redirects, including local testing through a secure tunnel. iCloud does not use OAuth.
4. Set `WEB_ORIGIN` to the web app's origin and restart/redeploy the API. Reload Connections, choose Connect, and grant access in the provider's own consent screen.

Provider registration details:

- [Microsoft identity authorization](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow): register a confidential **Web** app, supporting organizational and personal Microsoft accounts if both are needed. Delegated scopes are `Calendars.ReadBasic offline_access`. Outlook uses Microsoft Graph `me/calendarView` with UTC responses. It does not request write or mail access.
- [ClickUp authentication](https://developer.clickup.com/docs/authentication): a workspace admin/owner creates the OAuth app. Users choose authorized workspaces. ClickUp currently issues a non-expiring access token without a refresh token; Veylo only invokes read endpoints, although ClickUp does not offer granular read-only OAuth scopes.
- [Asana OAuth](https://developers.asana.com/docs/oauth): allow `tasks:read workspaces:read users:read`, register the HTTPS redirect, and ensure distribution permits the intended workspaces.
- [Trello confidential OAuth](https://developer.atlassian.com/cloud/trello/guides/rest-api/oauth-2-confidential-client-usage/): register a confidential OAuth 2.0 client with `read:member:trello read:board:trello read:card:trello offline_access`. Use the Trello client credentials, not the existing Jira client's credentials. PKCE is included.
- [Todoist API](https://developer.todoist.com/api/v1/): register an OAuth app with `data:read`. Veylo uses the v1 tasks endpoint, including its cursor-based pagination indicator. Non-expiring access tokens are supported.
- [Microsoft To Do](https://learn.microsoft.com/en-us/graph/api/todotasklist-list-tasks?view=graph-rest-1.0): register a Microsoft confidential Web app with delegated `Tasks.Read offline_access`. It can share an app registration with Outlook if both exact callback URLs and permissions are registered; the two Veylo connections store separate grants. Due dates are shown as calendar dates.
- [Linear OAuth](https://linear.app/developers/oauth-2-0-authentication): register a client with `read`, the exact callback, and PKCE. Store and rotate the refresh token. Queries read the signed-in user's assigned issues, excluding completed/canceled work.
- [GitHub App user authorization](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-user-access-token-for-a-github-app): create a **GitHub App**, configure repository Issues as read-only (Metadata is implicit), register the callback and install the app on the intended repositories. Use the App's client ID and client secret, not its numeric App ID or private key. No broad OAuth `repo` scope is requested. Both expiring user tokens with refresh and non-expiring tokens are supported. [Assigned-issues responses](https://docs.github.com/en/rest/issues/issues#list-issues-assigned-to-the-authenticated-user) can include pull requests, which Veylo excludes. Dates are milestone deadlines.
- [Slack OAuth](https://docs.slack.dev/authentication/installing-with-oauth/): add **User Token Scope** `search:read`, not a bot scope. Register the callback and permit installation for the desired workspace. Veylo extracts `authed_user.access_token` and supports token rotation. The permission can search messages accessible to the user, but Veylo's [search query](https://docs.slack.dev/reference/methods/search.messages/) is restricted to `from:me`. No bot, posting, or write scopes are requested. Workspace policy can require administrator approval.

### iCloud Calendar

Only `TOKEN_ENCRYPTION_KEY` is required on the API. In Connections, enter the Apple Account email and an [Apple app-specific password](https://support.apple.com/en-us/102654), which requires two-factor authentication. Never enter the main Apple Account password. The form clears the password after each attempt; credentials are verified through CalDAV before being encrypted in the database. They are not stored in browser persistence or returned through the catalog/status APIs.

Veylo invokes only PROPFIND and REPORT. App-specific passwords themselves are not calendar read-only grants. Discovery and redirects are restricted to HTTPS `caldav.icloud.com` and Apple's numbered CalDAV hosts. XML entities/DTDs are rejected and responses are size-limited. The server requests [CalDAV recurrence expansion](https://datatracker.ietf.org/doc/html/rfc4791#section-9.6.5); unresolved recurrence or local time values produce an explanatory error rather than incorrect dates. Disconnect clears Veylo's credential copy and reminds the user to revoke the app-specific password in Apple Account settings.

Tokens stay encrypted in the API database. Authorization states are owner-scoped, expire after ten minutes, and can be consumed once. Outlook, Asana, Trello, Microsoft To Do, Linear, and GitHub include PKCE. Expiring OAuth tokens are refreshed when needed. Disconnect immediately clears Veylo's saved tokens; the UI also explains removal from the provider's connected-app settings. Deleting a Veylo account reports the same remaining-grant guidance.

Validation without external accounts: `node --import tsx --test apps/api/test/connections.test.ts apps/api/test/work-connections.test.ts apps/api/test/icloud-calendar.test.ts apps/web/test/unit/connections.test.ts`. Live consent, iCloud discovery, and provider responses still need verification with configured accounts; mocked contracts do not establish that app registration or provider account policies are correct.
